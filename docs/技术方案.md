# nomedia-scan 技术方案

**目标**：一个安卓 App，用于「临时让某个含 `.nomedia` 的超大文件夹被系统媒体库扫描（从而能被网盘相册备份）→ 备份完成后恢复隐藏」。

**版本**：0.1.0-beta（先做可用 MVP）
**状态**：方案评审中（待确认后开工）

---

## 1. 项目背景与目标

### 1.1 场景

- 手机上有约 150G 的文件夹，结构为「大量子文件夹 → 图片文件」。
- 文件夹内存在 `.nomedia` 文件 → 系统 MediaProvider 不索引 → 图库不显示 → 网盘 App 的「相册备份」通道扫不到（网盘相册备份底层查 MediaStore）。
- 直接让网盘 App 备份该文件夹（SAF 授权路径）不稳定（超大目录遍历易崩）。

### 1.2 解决方案

临时移除/重命名 `.nomedia` → 触发 MediaProvider 重新扫描 → 图片进入媒体库 → 用网盘「相册备份」稳定备份 → 备份完成后恢复 `.nomedia` → 清理媒体库索引 → 图库恢复原样。

### 1.3 交付物

一个 Android App（APK），核心是三个动作：

1. **临时打开**：移出 `.nomedia` + 触发媒体扫描 + 显示扫描进度。
2. **备份窗口期**：等待用户去网盘 App 完成备份（App 提供状态提醒，防呆）。
3. **恢复隐藏**：移回 `.nomedia` + 清理媒体库索引。

两种权限模式，App 内可切换：

- **Shizuku 模式**（推荐）：shell 权限直操文件，秒级完成，适合超大目录。
- **SAF 模式**（低权限兜底）：无需 Shizuku，普通 App 权限，慢但零门槛。

## 2. 核心原理

### 2.1 `.nomedia` 机制

- `.nomedia` 是空文件（通常 0 字节）。MediaProvider 扫描目录时，若该目录或其任一**上级目录**存在 `.nomedia`，则跳过该目录整棵子树。
- 因此：**根目录一个 `.nomedia` 即可屏蔽整个 150G 目录**；若每个子目录都有（某些工具会批量生成），需全部处理。

### 2.2 触发媒体扫描（关键 API）

| 方法 | 兼容性 | 说明 |
|---|---|---|
| `MediaScannerConnection.scanFile(ctx, String[] paths, ...)` | Android 10+ 通用 | **主方案**。传目录路径在 Android 11+ 会递归扫描整棵目录树。App 需持有媒体读取权限 |
| `am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE` | Android 10 以下 | Android 11+ 已移除该广播，仅作 Shizuku 模式下的额外尝试 |

> 注意：`MediaScannerConnection.scanFile` 传目录递归扫描在各大 ROM 上表现基本一致，但对超大目录，**MediaProvider 存在扫描耗时、文件数上限、超时截断**等问题——因此必须**分批扫描**（见 §5.3）。

### 2.3 恢复后的索引清理

放回 `.nomedia` 后，对目录再触发一次 `scanFile`，MediaProvider 重新扫描该目录时会发现 `.nomedia` 并**删除该目录下已有媒体条目**。此为系统标准行为，双保险手段：

- Shizuku 模式：直接 `content delete --uri content://media/external/images/media --where "_data LIKE '/storage/emulated/0/xxx/%'"`，彻底清理（可同时清理 video 表）。
- SAF 模式：仅依赖重扫自动清理；若某 ROM 清理不彻底，提示用户在图库 App 设置里「清除缓存/清除数据」。

## 3. 功能需求

### 3.1 主界面（简单 3 段式）

- **状态区**：当前目标文件夹路径、`.nomedia` 状态（已移出 / 已恢复）、模式（Shizuku / SAF）。
- **动作区**：两个主按钮「临时打开」「恢复隐藏」+ 「重新选择文件夹」。
- **进度区**：子目录扫描进度列表（每子目录：状态 ✓/…/×、索引数/实际文件数），总进度条。

### 3.2 功能清单

| # | 功能 | 说明 |
|---|---|---|
| F1 | 选择目标文件夹 | Shizuku 模式：手动输入路径或 SAF 选择器；SAF 模式：`ACTION_OPEN_DOCUMENT_TREE` |
| F2 | 临时打开 | 移出所有 `.nomedia`（改名 `.nomedia.bak`，保留内容备份）→ 分批触发扫描 → 显示进度 |
| F3 | 扫描进度 | 轮询 MediaStore 计数 vs 实际文件数（Shizuku 下用 `find | wc -l`；SAF 下遍历计数），逐子目录显示 |
| F4 | 续扫 | 对未索引完的子目录单独重扫（应对 ROM 扫描截断） |
| F5 | 恢复隐藏 | 恢复所有 `.nomedia`（`.nomedia.bak` 改回 / 重建）→ 触发清理扫描 → 可选 Shizuku `content delete` 双保险 |
| F6 | 状态持久化 | 记住「已打开未恢复」状态；通知栏常驻提醒（防忘恢复） |
| F7 | 历史记录 | 最近操作过的文件夹与时间 |

### 3.3 防呆设计

- 打开状态必须醒目（红/黄色条 + 通知），提醒「备份完成后点恢复」。
- 恢复操作前置二次确认。
- `.nomedia` 内容先读入 App 私有目录备份，恢复时原样写回（保留原文件属性语义，如内容非空）。

## 4. 权限设计

### 4.1 存储/媒体权限（两种模式都需要）

| 权限 | 用途 | 系统版本 |
|---|---|---|
| `READ_MEDIA_IMAGES` | MediaScannerConnection 触发扫描 + MediaStore 计数查询 | Android 13+ |
| `READ_EXTERNAL_STORAGE`（maxSdkVersion=32） | 同上（旧版） | Android 12 及以下 |

- `targetSdk = 34`。Android 14+ 声明 `READ_MEDIA_IMAGES` 时用户需在系统弹窗选择「全部照片」，需在引导页说明。
- 不做写权限申请（改文件走 SAF 或 Shizuku，不需要 WRITE 权限）。

### 4.2 Shizuku 权限

- Manifest 声明：`moe.shizuku.manager.permission.API_V23`、`moe.shizuku.API_V23`。
- 运行时：`Shizuku.requestPermission()` 授权（用户需已安装 Shizuku 并通过 adb/无线调试激活）。
- Shizuku 模式下改文件不需要存储写权限（shell 身份直操 `/storage/emulated/0/...`）。

### 4.3 权限清单总结

| 模式 | 权限 | 安装门槛 |
|---|---|---|
| Shizuku | READ_MEDIA_IMAGES + Shizuku | 需装 Shizuku（激活一次常驻） |
| SAF | READ_MEDIA_IMAGES + SAF 授权 | 普通 App 直接装 |

## 5. 技术架构

### 5.1 技术栈

- Kotlin + 经典 View（Material Components），**第一版不用 Compose**（构建更快、APK 更小、依赖更少）。
- minSdk 26（Android 8），targetSdk 34。
- 依赖：`shizuku-api`（Shizuku 模式）、`androidx.documentfile`（SAF 封装）、`material`、`kotlinx-coroutines`。
- 无第三方网络/存储 SDK。

### 5.3 核心流程设计

#### 流程 A：临时打开

```
1. 校验模式可用性（Shizuku 是否授权 / SAF 是否已授权目录）
2. FileOp.listNomedia()  -> 得到所有 .nomedia 位置
3. FileOp.moveOut()      -> 逐个改名 .nomedia -> .nomedia.bak（内容先备份到 App 私有目录）
4. 收集顶层子目录列表 dirs[]（若为空则就扫根目录本身）
5. 分批：每批 5 个目录，逐批 MediaScanner.scanFile(dirs_batch)
   每批间隔 3~5s，防止 MediaProvider 队列被打爆
6. 每批后刷新 MediaStore 计数，更新进度 UI
7. 全部完成后 -> 状态置为「已打开」，弹通知提醒「去网盘备份，完成后点恢复」
```

#### 流程 B：恢复隐藏

```
1. 二次确认
2. FileOp.restore()      -> 所有 .nomedia.bak 改回 .nomedia（内容用备份写回）
3. 触发清理扫描：scanFile(根目录) 让 MediaProvider 发现 .nomedia 并清索引
4. Shizuku 模式附加：content delete 清理 images/video 表（_data LIKE '根路径/%'）
5. 验证：查询 MediaStore 计数应趋近 0；通知「已恢复隐藏」
```

#### 流程 C：进度监控

- 实际文件数：Shizuku 模式 `find 根路径 -type f | wc -l`；SAF 模式遍历 `DocumentFile.listFiles()` 累计（慢，放后台协程，逐层累计）。
- 已索引数：`MediaStore.Images` + `MediaStore.Video` 中 `_data LIKE '根路径/%'` 的 count（ContentResolver query + COUNT(*) projection）。
- 进度 = 已索引数 / 实际文件数；子目录粒度显示。

### 5.4 关键实现细节与已知坑

| 坑 | 对策 |
|---|---|
| `MediaScannerConnection.scanFile` 传目录在个别 ROM 不递归 | 批内直接传「所有叶子子目录路径」数组，不依赖递归 |
| MediaProvider 扫描有数量/时长限制（MIUI/ColorOS 常见） | 分批 + 间隔 + 进度显示 + 可对未完成子目录单独续扫 |
| Android 14+ 授权弹窗默认「选择照片」，需「全部照片」 | 引导页说明 + 检测授权类型（`MediaStore.canManageMedia`? 不适用，用 `readMediaImages` 全量判断） |
| SAF treeUri 解析真实路径（`primary:xxx` / `raw:...`） | 双格式解析函数，解析失败 fallback 用 treeUri 本身查询 `_data` |
| 通知常驻被系统清理 | 用前台服务持有通知（`FOREGROUND_SERVICE` + `POST_NOTIFICATIONS`） |
| 扫描期间用户误操作 | 打开状态下禁用「重新选择文件夹」，主按钮高亮 |

## 6. 风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 150G 索引耗时（估 20min~数小时） | 高 | 分批+进度；提示用户期间少动手机；可中断续扫 |
| ROM 扫描截断（只索引一部分） | 高 | 子目录粒度续扫；Shizuku 模式可脚本化全量 `find` 触发（若 ROM 支持） |
| 网盘备份画质被压缩 | 中 | 提示用户网盘设置里选「原图备份」 |
| 忘记恢复 `.nomedia`（图库长期暴露） | 中 | 状态持久化 + 通知栏常驻 + 恢复按钮醒目 |
| SAF 模式大目录遍历慢/ANR | 中 | 后台协程 + 进度；提示优先用 Shizuku 模式 |
| 某些 ROM 图库有自己的缓存（恢复后仍显示） | 低 | 引导清理图库 App 缓存/数据 |
| Shizuku 未激活/授权失败 | 低 | 模式切换时引导用户打开 Shizuku 激活 |

## 8. 里程碑计划

### M0 原理验证（开发 app 前，最重要）

做一个**最小扫描触发器 App**（单按钮：对指定目录调 `MediaScannerConnection.scanFile`），在用户手机上实测：

1. 移除 `.nomedia` 后，`scanFile(目录)` 是否成功索引（小目录先试）。
2. 索引耗时与数量上限表现 → 决定分批粒度。
3. 放回 `.nomedia` 后重扫，索引是否被清理（各 ROM 行为）。
4. 顺便验证用户网盘 App 的「相册备份」是否能扫到这些图片。

> 该最小 App 就是正式 App 的 `MediaScanner.kt` 雏形，不浪费。

### M1 MVP（0.1.0-beta）

- 完整三流程 + 进度 + 状态持久化 + 通知。
- 两种模式（Shizuku / SAF）都实现。
- 真机测试：先用一个小目录（几百 MB）全流程验证，再上真目录。

### M2 打磨
